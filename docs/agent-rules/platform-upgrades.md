# 基座升级、兼容与二开迁移

继承[总规则](../../AGENTS.md)。基座维护者对承诺的兼容窗口负责；二开维护者固定版本，并在自己的适配层处理旧新契约差异。

## 基座维护者：先判定影响，再发布

- 清点对外契约：Java API/SPI、SDK 和宿主能力，REST 路径与请求/响应/状态码，事件类型及持久化载荷，权限 key，配置 key/单位/默认值，MySQL schema、规则文档及插件清单/签名协议。签名结构、授权范围、默认行为的改变也可能破坏兼容。增加 Java record 字段、枚举值或 JSON 字段时实测旧编译产物和严格解码端。
- 新增模块、表、路由、权限、配置或能力 ID 前，核对各二开项目登记的命名空间；用实际装配验证扫描、路由及迁移无冲突。发现撞名优先为新增资源换名；已上线名称须保留兼容映射并迁移调用方，避免两个实现依赖扫描或加载顺序抢占。
- 优先以新增方法、独立版本、适配器或弃用桥接演进。旧 API 在约定窗口内保留原语义；不要把兼容逻辑散布到各客户实现。必须破坏时，明确新的契约版本、迁移责任人、支持范围、截止版本、发布顺序和停止条件。当前项目仍有开发期 `SNAPSHOT`，不要把这份规则描述成已有的版本兼容承诺。
- 有版本耦合的宿主/发布服务/worker 以经验证的同批构建或明确的兼容组合部署。变更 SDK 主版本时先验证宿主是否仍支持旧插件；不能把仅支持 `sdkMajor: 1` 的当前准入当成双主版本支持。若不支持共存，安排业务重新构建、签名和验证，或保留旧宿主并隔离流量。
- 发布说明须包含旧/新行为、受影响业务、替换 API 或映射、配置和数据转换、兼容窗口、可用的旧制品与回退方法。未给出迁移路径的破坏式改动不进入普通兼容更新；安全原因必须缩短窗口时明确影响与替代方案。

## 二开维护者：处理破坏式更新

1. **冻结可工作的组合。** 保存上一版基座、业务包、SDK、配置及迁移历史的版本/摘要；用独立验证环境复现现状，准备可恢复的脱敏数据快照。先读取变更说明和实际差异；同仓二开在独立业务升级分支验证目标基座版本，见[分支与合并](secondary-development.md#分支与合并)。
2. **定位断点。** 逐项排查编译/二进制链接、REST 与权限、配置绑定、数据库/事件、插件入口/SDK、前端协议和旧任务。把变更映射到自己的业务依赖；基座缺兼容点时提交独立的基座变更或暂留旧基座。
3. **在业务侧适配。** 将旧调用集中到版本适配器，改为新契约。若需跨版本共存，验证旧配置与历史数据可读、缓存分版本隔离、未完成事件可消费、旧工作仍指向原版本。数据按[扩展、回填、收缩](data-and-configuration.md#flyway-与共存)实施，禁止通过修改已执行脚本、历史版本或全局配置掩盖问题。
4. **跑迁移矩阵。** 对比旧基座+旧业务基线、新基座+旧业务（升级兼容或明确阻断）、新基座+新业务目标；如允许回退基座或先升级业务，加测旧基座+新业务和真实回退路径。对不支持的组合，记录失败表现、部署顺序和流量隔离条件。用真实制品跑旧库升级、关键业务链路、租户隔离、在途/重试和回退演练。
5. **分阶段切换。** 先兼容准备，再升级基座和业务，按已验证顺序切换或灰度。检查接口拒绝率、关键结果、迁移状态和新旧版本引用。未达通过条件时停在可用组合；确认旧消费者与业务工作退出后再移除兼容层。

例：基座把 `customerId` 改为 `accountId`，先在公开契约新增新字段并维持旧字段语义；业务适配器接受受支持的旧新载荷，持久化按新增字段、分批回填、双版本验证执行。待旧业务和积压事件退出、回退窗口关闭后，再独立发布删除旧字段的变更。

## 回退必须分层

- **基座/静态业务包**：应用包可退到已验证的版本组合。只要新版写过旧版无法读取的数据，单退 JAR 就不是完整回退。保留新旧都能读取的 schema；需要恢复库时先隔离写流量，确认快照时间点、切换后写入的保全与补录方案。
- **插件与规则**：插件通过签名发布链选择历史稳定向量，并增加发布修订；规则使用规则平台的回滚接口。二者都保留历史，均不反向撤销已提交业务数据或外部动作。
- **事件与在途工作**：未确认副作用先向业务权威来源对账；恢复任务使用原契约、原幂等键或明确补偿流程，不通过清空引用、修改版本指针或重发新键强行恢复。

升级记录至少包含：`旧组合 → 新组合 | 影响项与对应改法 | 迁移和验证证据 | 回退条件与动作 | 责任人及兼容截止点`。没有通过验证的组合不可写成已兼容。
