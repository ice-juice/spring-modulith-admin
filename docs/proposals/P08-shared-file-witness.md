# P08 共享文件部署见证

属于已授权P08的M2c/M3范围；当前是细化方案，实施和验收状态以[进度](../cache-governance-progress.md)为准。复用已有File存储与上传协议，不另建上传链，不把P09尚未完成的云传输能力当作已交付。

## 路径与边界

- `common/deployment/`：宿主可信启动SPI，只交换资源标识、节点/进程标识和小型见证摘要，不暴露磁盘路径、文件正文或存储凭据。
- `file/internal/service/`：部署共享声明及本地见证适配，读取既有FileProperties和StorageSettings；不替换LocalStorage、LocalTransferStorage和上传任务协议。
- `file.storage-witnesses`：在既有缓存目录登记为PROTECTED；不能借普通清缓存删除持久文件或共享见证。
- 后续M3在Common集群预检中调度见证并判断就绪；M2c提供契约和实际文件级证明，M2d再做A上传/B经原授权接口下载的验证。

## 明确共享声明

建议部署键`sma.file.cluster.shared-resources`列出明确声明共享的资源：`file.legacy`对应既有`sma.file.directory`；`file.local.<alias>`对应P09已有`sma.file.storage.local-roots`别名。缺省为空，不推断为共享。声明未知资源拒绝，不能以相同路径字符串或相同盘符当作跨主机共享证明。

单实例保持原行为，未触发集群探针时不创建额外目录。multi必须同时通过声明和实际见证；任何新增本地存储别名都需要进入同一检查范围，不能因新上传路径绕过集群约束。云提供方仍按各自已验证适配器能力处理，不借这个SPI宣称支持所有对象存储。

## 有界见证协议

每个进程使用固定本次进程标识和随机32字节挑战，在已声明资源下写入专用隐藏目录。目录同时绑定部署分组、资源、node ID和process ID；所有路径分量由服务端校验/摘要生成，不接受HTTP路径。公开摘要为SHA-256，其他节点必须实际读取并核对；A写B读与B写A读各有证据。相同进程/挑战的重复调用只核对原文件，发现不同字节或不确定写入不能覆盖。

仅允许既有根目录，尤其不能在共享挂载缺失时自动新建一个本地根目录冒充成功。逐级检查目录，拒绝符号链接/junction等重解析跳转；见证文件使用排他创建、无跟随链接、有界长度和文件锁，并在成功前刷盘。读取最多33字节以判断超长，摘要/长度不符、只读挂载、锁冲突和I/O失败均不能确认共享。需要有限执行并发和截止；超时不派生无限替代线程或重做未知写入。

只清理本进程明确创建且验证归属的单个见证，不递归删除共享目录；崩溃留下的旧标识由后续受信名册维护处理，普通缓存清理不参与。这里的见证是部署技术状态，不是认证令牌，也不是用户文件。

## 验收与承诺范围

1. 两个独立适配器访问同一临时目录能互相验证，访问不同目录失败；资源/分组/节点/进程混用、错误摘要、覆盖尝试和路径逃逸拒绝。
2. 本机可实际创建的符号链接或junction须验证；平台限制导致某项无法运行时记录跳过，不宣称全平台通过。
3. 两JVM经原上传协议在A写入，B通过权限/租户检查后返回相同字节；回执UNKNOWN不重传，未授权者不能借共享目录获得文件。
4. M3核对节点的实际共享结果、错误挂载和重启；健康B不能只因A离线而丢失既有可用资格，新的进程仍要重新证明。

见证只证明当时指定资源的跨进程读写与锁行为，不证明存储供应商的持久性、全盘一致性、跨可用区HA或零RPO。同机双JVM通过不能替代真实生产挂载及多主机验收；运行手册必须写明此边界。

## M3b3落地顺序与失败语义

M3b3a先实现Common内部的受信存储注册与每进程探针：验证真实提供模块、固定资源集合且所有资源显式共享、总数最多32；至少包含基座file.legacy。每资源生成独立32字节随机挑战，实际路径Scope绑定manifest、node、process及租约epoch（manifest+epoch派生group，process保持真实UUID）。公开报价只含身份与资源摘要，不含原挑战/路径。初始化写入每资源最多一次；写结果未知后只允许verify同一摘要，不能自动重建消失文件或覆盖。自身见证每轮重验，peer报价必须来自后续存储读取的受信清单并精确匹配manifest/预期node/进程/epoch和资源集合。peer验证仅代表单向读取，不能直接标READY。

M3b3b将报价、双向确认与资格绑定已有节点租约/部署配置MATCH，追加Common迁移；初次及进程更替必须有当前活peer的反向确认，不能继承旧进程资格。已证明节点可在peer离线时继续自检既有见证，但自身读写失败必须失去资格；恢复须按同一围栏协议重新确认。错误新节点不得撤销健康peer。所有I/O在事务外，持久报告重查身份/代次/截止，循环/线程/记录数量有界。

M3b3c接独立有界worker与健康状态，最后双JVM真实相同/不同/缺失目录、删除自身探针、重启与健康peer持续访问。b3a的本地I/O测试不替代b/c或生产多主机挂载证明。崩溃残留探针不通过自动递归清理删除；后续清理必须单独核验退役身份及原摘要。改动限Common部署协调、现有File见证适配和相关测试/文档，不改P09上传协议。

持久互证还需避免两个隔离目录中的两对节点各自互证就被当作同一个共享存储：b阶段将由配置清单指定引导节点建立每清单不可替换的存储锚点报价，所有成员必须读取同一锚点的全部资源，并与当前有效peer完成双向确认。锚点文件随清单存续，不因引导进程退出删除。节点自身故障须推进报告代次并废弃旧互认；只保留健康节点自身连续校验下的既有证书，新的process/epoch和故障恢复不能借历史peer确认跳过重验。此处是下一子项约束，a阶段不实现或宣称资格证书。

M3c1接流验收补充：不可变见证的verify使用共享读锁，避免多个节点同时读取固定锚点互相撤销资格；首次写、publish已有文件核对及retire仍用排他锁。打开见证仍要求READ/WRITE权限，长度/摘要/force及无链接检查保留。挂载不支持共享锁时拒绝资格，不静默退回排他读取。FileClusterStorageTests以独立子JVM持共享锁验证12次读取均通过，同时发布/退役必须拒绝；原排他锁占用仍拒绝。Java本身禁止同JVM重叠FileChannel锁，生产每节点见证运行时仍是单worker顺序核验；这不是任意同JVM并发持锁API。实际多主机挂载仍需独立验收。
