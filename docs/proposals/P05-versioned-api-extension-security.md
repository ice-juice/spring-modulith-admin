# P05 业务模块热更新、JAR 分组与安全发布架构方案

- 日期：2026-11-10。
- 状态：修订版 v3；面向通用业务扩展，首版资源与安全规则已按用户授权给出默认设计；未实施，不代表已有安全控制。
- 适用系统：Springboot Modulith Admin，Java 21 / Spring Boot 4.1.2 / Spring Modulith 2.1.2。
- 已确认的需求：公司内部可信开发人员上传 Java 文件或 JAR；支持不限于 API 的通用业务模块扩展；JAR 按分组管理；支持版本、灰度及回滚；核心认证与发布管理默认不插件化；已授权用户通过操作验证即可上传和发布，不设置双人审批。
- 范围澄清：计费、风控只是用户说明扩展能力的例子，不是待开发业务；不建设这些业务的模块、页面、指标或专项验收。本方案只规定通用扩展底座和通用验证样例。
- 已确认的现状与偏好：没有现成 IdP / WebAuthn / TOTP、制品仓库、CI、KMS 或独立审计服务；当前不要求业务插件采用独立进程；稳定性与安全性优先。
- 用户授权按通用情况设计 JAR 配额、依赖白名单、漏洞阻断阈值和临时例外期限，第 19 节据此给出可直接用于首版实现的默认规则，无需再次逐项确认；上线前仍应通过验证，后续按策略修订优化。部署条件与实际业务契约不作臆测。文件名保留原路径，避免既有链接失效。
- 本次交付仅为方案文档；不新增接口、数据库表、前端页面、运行配置或依赖。

## 1. 决策摘要

采用“稳定业务契约 + 多版本插件运行时 + 分组管理 + 独立可信发布链”。API、内部服务调用、事件处理和定时任务均可作为业务入口。首期业务插件运行在宿主 JVM 内，只允许通过受控校验、签名和发布授权的内部制品进入主进程。

核心决策：

1. 不直接替换宿主已加载类；指定业务处理器以多个版本并存，通过路由切换生效。
2. Java 文件先在隔离构建环境编译，最终与上传 JAR 一样形成不可变插件制品。
3. 普通文件上传、文件落盘、数据库登记、制品签名均不等于获准加载。加载还必须具备面向当前环境的有效发布授权。
4. 上传、发布、灰度、放量、回滚、撤销和信任配置变更分别授权。同一名已授权用户可上传并发布自己的制品；每次敏感动作完成绑定本次内容的强化认证，不等待第二个人审批。
5. 生产签名私钥、关键发布授权及独立审计位于业务服务器之外。业务数据库和业务服务器本地目录不作为发布信任根。
6. 当前不引入业务插件独立执行进程。同 JVM 方案只能约束正常加载路径，不能隔离恶意代码或在宿主已被完全控制后证明其可信；主机失陷后按事件响应流程恢复。发布安全服务与隔离构建器独立部署是信任链要求，不等于业务插件必须进程隔离。
7. 没有现成基础设施时，建设最小发布安全服务，内置操作密码、TOTP、授权、签名和审计，避免首期依赖一整套企业 IdP / CI / KMS 产品。
8. 核心认证、发布控制、验签和审计信任链默认不插件化。通用业务算法、策略和编排可热更新，持久提交、幂等和权限执行等稳定约束由宿主掌握；不据此新增任何具体业务。

首次接入运行时、改造已有业务模块需要一次正常部署。此后只有满足插件契约的变更承诺宿主免重启。这里的“业务模块”是可版本化的一组实现，不表示任意已有 Spring Modulith 包、Bean、Mapper 或数据库结构都能直接替换。JDK / Spring 升级、宿主 SDK 破坏性变更和破坏性数据库迁移仍走常规部署。

## 3. 威胁模型与能力边界

“内部可信开发人员”描述正常使用者，不等于账号、浏览器、开发机、构建环境永不失陷。必须防范盗用账号、依赖投毒、越权发布和服务端漏洞。

| 攻击者获得的能力 | 目标防护 | 实际边界 |
|---|---|---|
| 未登录访问、普通用户、普通租户管理员 | 网络入口限制、默认拒绝、平台级授权、请求限流 | 前端隐藏按钮不构成授权 |
| 窃取登录令牌 | 操作密码 + 独立认证因素、动作绑定、单次授权 | 若浏览器和认证流程同时受控，TOTP 仍可能被实时钓鱼 |
| 向普通上传目录写入 JAR | 不扫描目录、不自动加载；隔离存储；只消费已授权摘要 | 文件扩展名、文件名和“在插件目录里”均不构成信任 |
| 修改业务数据库或发布状态字段 | 外部发布授权、签名清单、修订及撤销状态复核 | 本地数据库中 active=true 不能让代码获得执行权 |
| 低权限主机账号、替换本地插件文件 | 服务身份分离、只读制品、加载时验签验摘要、权限与路径约束 | 若攻击者具有与主进程相同的调试 / 写内存能力，已超出普通文件篡改情形 |
| 已在宿主 JVM 任意执行代码，或取得宿主服务账号的等效进程控制权 | 外部签名密钥隔离、独立审计、告警与隔离，限制横向扩散 | 可以自行定义类、修改内存或绕过正常加载器；不能承诺阻止其加载任何类 |
| 服务器 root / Administrator、内核或虚拟化层失陷 | 外部控制面、网络侧阻断、凭据撤销与干净重建 | 本机校验、公钥、二进制、时钟和日志均可能被篡改；不能继续信任该节点 |
| 构建系统或签名服务失陷 | 分离制品证明与发布授权、动作验证、来源记录、密钥撤销 | 合法签名不能证明代码无恶意；单人模式不提供第二人复核，不能防止一个拥有足够权限的恶意内部人员主动发布恶意代码 |

禁止将 ClassLoader、字节码静态扫描、SecurityManager 或自定义 API 白名单描述为可靠 Java 安全沙箱。静态检查只能发现部分风险，不能证明恶意 Java 安全。

## 4. 逻辑架构与生产信任边界

### 4.1 组件职责

| 组件 | 职责 | 不应持有的权限 |
|---|---|---|
| 发布管理界面 / API | 展示制品、形成发布意图、触发验证、查询执行状态 | 不持有签名私钥；不能自行生成可信验证成功证明 |
| 隔离上传区 | 接收通过上传授权的原始文件，按摘要记录 | 不进入宿主 classpath，不被运行时扫描 |
| 隔离构建与验证服务 | 固定工具链编译、依赖解析、扫描和契约测试 | 不持有生产数据库凭据、部署管理员权限或发布私钥 |
| 制品仓库与验证签名服务 | 保存不可变制品、来源及构建 / 导入验证证明，签署制品摘要 | 制品证明不授予任何环境的加载权限 |
| 发布安全服务 | 独立验证高权限身份、操作密码 / MFA、分组和环境权限及发布策略，签发环境限定发布清单 | 不能只信任业务服务提交的 userId、角色、mfaPassed=true |
| 宿主插件运行时 | 验证制品及发布清单、加载、预热、选版、排空 | 不允许任意路径 / URL 加载，不持有构建或发布签名私钥 |
| 独立审计 / 告警系统 | 保存发布证据、异常信号、节点状态 | 普通业务账号和插件不能删除或改写已接收事件 |

生产推荐：业务宿主、构建执行器、发布授权及密钥服务位于不同安全边界，至少不共享系统账号、写目录和管理凭据。仅拆成同一服务器上的几个进程不足以抵抗服务器管理员失陷。

当前没有企业 IdP / MFA / CI 等基础设施，由最小发布安全服务承担关键认证与授权。它自行验证用户身份和发布范围；主应用的服务身份只能创建动作意图、查询状态和拉取明确授权的结果，不能成为通用签名代理。具体从零建设范围见 4.3。

关键发布角色由独立控制面的可信目录授权，IAM 可以展示或映射这些角色，但修改业务库角色或设置本地 superAdmin 不能直接获得生产发布权。身份变更与吊销需要有明确同步及最长失效时限。

开发演示可将组件合并部署，但必须标明安全能力降低；生产环境不允许自动降级到本机私钥或跳过独立授权。

### 4.2 操作与加载链路

1. 管理员登录，界面展示其被授予的插件、环境、动作范围。
2. 创建上传意图；操作密码及二步验证成功后签发一次性上传许可。
3. 原文件仅进入隔离区，服务器计算摘要并与许可约束核对。
4. 源码构建或 JAR 导入验证成功后形成不可变制品及对应证明签名；失败制品不可推进。
5. 发布人创建精确发布计划：目标环境、制品摘要、配置摘要、灰度规则、预期基础修订等。
6. 同一发布人查看准确计划并完成本次操作密码与第二因素验证，不需要其他人批准。
7. 发布安全服务自动核验当前角色、分组范围、策略门禁与最新状态，签发环境限定发布清单。
8. 节点下载到暂存区，核验签名、摘要、依赖、撤销及兼容性，通过后才允许定义插件类和初始化。
9. 初始化无副作用，预热只使用隔离数据或只读能力；节点报告就绪。
10. 发布修订生效，入口固定版本处理请求；旧版本停止接收新请求并排空。

上传成功、测试成功、签名成功、节点就绪、发布生效是不同状态，界面与审计均不能混用。

### 4.3 没有现成基础设施时的最小建设方案

| 能力 | 首期方案 | 不要求先采购 / 搭建的系统 |
|---|---|---|
| 发布身份与权限 | 发布安全服务维护独立高权限账号、分组 / 环境授权及与主账号的显式绑定 | 完整企业 IdP / 单点登录平台 |
| 二步验证 | 内置标准 TOTP，使用成熟库并兼容常用验证器 App；WebAuthn 后续增强 | 企业 MFA 服务或首期硬件密钥 |
| 制品仓库 | 按 SHA-256 寻址的私有文件 / 对象存储，版本不可覆盖，下载需授权 | Nexus / Artifactory 等完整仓库产品 |
| 构建验证 | 固定 JDK / Maven / 插件 SDK 的短生命周期隔离任务，依赖来自受限代理 | Jenkins 等完整 CI 产品 |
| 签名与密钥 | 安全服务上的专用密钥存储及成熟签名库，构建证明和发布使用不同密钥 / 用途 | 首期商用 KMS / HSM |
| 审计 | 安全服务持久记录，业务身份只能追加，定期向业务宿主不能改写的目标归档 | 独立大型 SIEM 平台 |

建议生产最小拓扑：业务宿主节点 + 独立管理边界的发布安全节点 + 隔离构建执行器。制品仓库和审计服务可先归入安全节点；构建器不与签名服务共享可写目录、密钥或特权凭据，不执行在签名服务进程内。未经信任的编译 / 构建应放在另一隔离 VM / 服务中；与安全节点共用可逃逸的特权容器不满足要求。

安全节点首期使用软件密钥，密钥文件加密、严格 ACL、由受控启动流程解锁，备份材料与密文分开保管。应用读取该密钥后仍会在内存中使用，不能将其描述成硬件级不可导出密钥，也不能声称能防安全节点管理员窃取。业务宿主不能取得密钥、解锁材料或安全库写权限。

发布验证在安全服务自己的可信 HTTPS 页面 / 来源完成，浏览器直接提交操作密码和 TOTP，业务服务不代收这些秘密。主界面可跳转并通过动作 ID 查询结果；不能用 URL 中的 verified 标记或前端消息冒充验证完成。无企业 SSO 时，首次绑定与重新登录通过安全服务自身账号流程完成。

初始化由运维通过受控本机 / 管理终端的一次性引导流程建立首个安全管理员并绑定 TOTP；完成后关闭引导入口，不能暴露长期“初始化管理员”接口。后续授权、因素重置和信任更新由具有相应权限的一名管理员强化验证后操作，均审计，不引入第二人审批。紧急恢复采用预置一次性恢复材料和受控运维身份，不接受仅修改业务数据库完成恢复。

生产业务宿主被攻陷后，安全节点仍需依靠独立网络身份和管理权限保持隔离。若只能使用同一台且同一管理边界的服务器，则可以开发验证，但不能声称抵抗服务器 Administrator / root 失陷。该部署条件仍待明确。

## 5. 防止外部 JAR 进入主进程

### 5.1 唯一受控加载入口

- 禁止监听目录自动加载、启动时扫描全部上传文件、接受任意本地路径 / URL、运行时从公网解析 Maven 依赖。
- 加载请求仅引用已登记的制品摘要与有效发布修订；存储位置由服务端可信配置解析，不使用客户端路径拼接。
- 禁止从普通附件系统、消息附件、临时目录、Web 根目录、当前工作目录发现可执行扩展。
- 插件包不得通过 Manifest Class-Path、嵌套依赖、服务发现、反射配置等绕过已声明且已签名的依赖闭包。
- 首期拒绝 Java Agent、动态 attach、JNI / 本地库、启动器、框架覆盖包以及未经授权的注解处理器；这属于准入约束，不是对恶意代码的完备隔离。
- 验证之前不实例化插件、不执行 static 初始化、不运行其 ServiceLoader 扩展。解析元数据使用受限纯数据格式，禁止反序列化上传的 Java 对象或执行模板表达式。
- 运行时加载后的依赖发现也必须受约束，不仅检查最外层 JAR。

### 5.2 验签与防替换

- 两类证明分开：制品签名证明“哪些字节经过哪个受控构建或导入验证流程”；发布签名证明“这些字节由哪名有权用户验证后授权在什么环境以什么配置和策略执行”。
- 推荐对确定格式的规范化清单签名，绑定制品摘要、全部私有依赖摘要、SDK 及配置摘要。可额外采用 JAR 签名，但不能只检查“JAR 内存在签名文件”。
- 使用成熟签名协议和密码库，明确签名算法白名单、keyId、证书 / 公钥来源、信任轮换、过期及撤销语义；不自行拼接容易产生歧义的待签名字符串。
- 生产公钥信任集随受控宿主部署或经安全管理员动作验证后更新；信任更新必须由既有可信根授权，不能以新上传公钥自证可信。不从上传 JAR、业务参数表或普通用户请求中导入信任根。
- 内容寻址存储、同版本摘要不可覆盖；构建结果修复后必须产生新版本或新制品标识。
- 下载后、进入加载前再次核验。使用服务端生成目录、验证后的完整快照和原子提升；运行账号对最终制品只读，避免“检查文件 A、实际加载已被替换的文件 B”。
- 后续惰性类加载也只读取该不可变快照。只在第一次加载前算一次摘要、随后继续读可写 JAR，不满足要求。
- 路径规范化并拒绝越界、符号链接 / Windows 重解析点逃逸、解压目录穿越、压缩炸弹、重复歧义条目；限制单包大小、展开大小、文件数、压缩比和解析时间。

### 5.3 宿主与部署加固

- 宿主使用专用低权限服务账号，不与构建器、制品写入器、运维交互账号共享身份。运行账号不能改应用二进制、启动脚本、公钥信任文件或最终制品目录。
- 生产应用及运行时镜像固定版本，根文件系统尽量只读；可写目录不进入 classpath。Linux noexec 不能阻止 JVM 读取并执行 JAR，不能当成主要控制。
- 启动来源固定并审计 `JAVA_TOOL_OPTIONS`、`JDK_JAVA_OPTIONS`、`_JAVA_OPTIONS`、classpath、javaagent / agentlib 等参数。现有开发 UTF-8 环境配置与生产受控启动配置分开管理。
- 在目标 JDK 和运维工具验证兼容后禁用不必要的 Attach 能力；关闭或严格隔离 JDWP、远程 JMX、危险 Actuator 端点和堆转储访问。此类加固不能对抗 root。
- 限制进程调试、跨账号访问、容器特权、宿主挂载及 Docker socket；必要时使用 SELinux / AppArmor 或 Windows 服务 ACL / 应用控制策略，并在目标平台实测。
- 管理入口仅允许企业网络 / VPN / 受控网关；业务端口不直接暴露发布控制接口。服务间使用独立身份与 TLS，重要链路使用 mTLS。
- 宿主及构建器出站网络按需允许。扫描和预热任务不可接触生产密钥、云元数据凭据或无关内网服务。
- 框架 / 依赖漏洞、反序列化、表达式注入、命令注入和任意文件写漏洞仍需持续修复；插件签名不能代替通用应用安全。

## 6. 分组管理权限与单人授权发布

### 6.1 权限粒度

建议 `extension` 作为模块 id，权限前缀与现有规范一致：

| 权限 | 含义 | 建议角色 |
|---|---|---|
| `extension:group:read` | 查看被授权的 JAR 分组 | 开发者、发布者、审计员 |
| `extension:group:manage` | 创建、重命名分组及管理归属 | 平台管理人员 |
| `extension:group:grant` | 授予分组 / 环境 / 动作权限 | 安全管理员 |
| `extension:artifact:read` | 查看制品、验证及脱敏状态 | 开发者、发布者、审计员 |
| `extension:artifact:upload` | 创建上传许可并提交指定范围制品 | 开发者 |
| `extension:artifact:validate` | 发起隔离构建 / 校验 | 开发者、构建服务 |
| `extension:release:propose` | 创建发布计划 | 开发者、发布者 |
| `extension:release:publish` | 验证并执行指定发布计划 | 发布者 |
| `extension:release:canary` | 执行已授权灰度计划 | 发布者 |
| `extension:release:promote` | 扩大流量、全量 | 发布者 |
| `extension:release:rollback` | 切回已授权兼容版本 | 发布者、应急人员 |
| `extension:runtime:quarantine` | 隔离指定版本 / 节点 | 安全人员、受限自动控制器 |
| `extension:artifact:revoke` | 撤销制品执行资格 | 安全人员 |
| `extension:policy:manage` | 变更认证、发布范围及保护策略 | 安全管理员，需动作验证 |
| `extension:trust:manage` | 密钥信任、签名来源与撤销 | 安全管理员，需动作验证 |
| `extension:audit:read` | 查看及受控导出审计 | 审计员 |

权限还必须限定分组、环境、插件、业务能力和目标范围。测试环境上传权不能推出生产发布权；一个插件的管理权不能操作另一个插件。允许同一用户拥有上传和发布权限，操作密码或 TOTP 本身不授予其原本没有的权限。

执行器影响的是进程或环境，不能把它视为普通租户业务功能。普通租户管理员无权上传、发布或加载 JVM 代码。即便灰度仅针对一个租户，同 JVM 插件仍可能影响整个宿主，不能据此下放平台执行权。

现有超级管理员语义不自动绕过操作验证、受信签名或环境范围。关键授权还由发布安全服务复核。不存在待审批队列、批准者角色或必须另一人操作的隐含条件。

### 6.2 单人操作规则

- 已授权用户可自己上传、创建计划并发布自己的制品；上传和发布分别验证，不能把上传验证直接当作发布授权。
- 自动策略门禁检查签名、兼容性、漏洞、资源和灰度约束。不存在人工二次审批，但也不能通过输入正确 OTP 跳过失败的技术校验。
- 授权绑定精确制品、配置及策略。替换制品、扩大范围、改灰度名单、增加宿主能力或变更基础修订，都要重新形成意图并强化验证。
- 允许用户一次验证授权一个范围明确、有时限和上限的自动分阶段计划；首期默认人工推进，每次人工放量重新验证。自动执行只能使用受限工作负载身份，不能伪造人工 OTP。
- 授予关键角色、调整认证策略、重置 MFA、变更信任根本身是受保护动作；由有相应权限的一名管理员验证后执行，不能用普通用户编辑接口绕开。

### 6.3 分组、插件与发布组的关系

管理层级为：业务分组 → 逻辑插件 → 不可变制品版本 → 各环境发布记录。分组名称由实际项目定义；文档可用“分组 A / 插件 A”演示，不预置用户未要求的业务模块。每个插件可包含多个类和一个或多个声明的业务入口，无需伪装成 HTTP API。

- 分组是管理与权限边界，不是 ClassLoader 或安全沙箱。同组不同 JAR 仍默认隔离类加载，不共享任意内部类。
- 首期每个插件只有一个主分组，可增加标签辅助检索；插件 ID 全局稳定，分组 ID 不因显示名变更而改变。
- 分组管理员不自动获得发布权；新分组默认无发布授权。分组授权由安全服务保存，主库仅保存展示投影，禁止修改主库 groupId 获得权限。
- 插件移组要求同时具备源 / 目标管理权并完成强化验证，目标运行权限必须显式确认；变更权威归属修订，作废未执行动作授权，历史发布保留原分组快照，运行版本不因移组自动切换。
- 分组停用首先阻止新上传和新发布，不隐式停止已运行业务。停止现有运行实例必须是另一个明确动作；有活跃版本、业务引用或审计保留要求时禁止直接删除分组 / 制品。
- 批量操作显示精确插件和版本清单，绑定整批摘要，不对未来新增成员自动生效。“一键发布整个分组”不能忽略逐插件就绪和依赖校验。
- 需要协同切换的业务插件组成单独的“发布组”，其中记录插件版本向量及依赖约束。管理分组不等于发布原子单位；跨分组发布组要求同时拥有所有目标权限。

## 7. 操作密码与二步验证

### 7.1 建议认证基线

“操作密码”是每名操作人的独立敏感操作凭据，不使用全员共享发布口令，不允许运维把口令写入配置或脚本。登录密码和操作密码都属于知识因素，两者相加仍不构成真正的双因素认证。

首期基线为：有效登录会话 + 当前分组 / 环境 / 动作权限 + 独立操作密码 + TOTP。没有企业 MFA 平台也可以通过内置 TOTP 与验证器 App 实现，不依赖短信服务。以后可增加 WebAuthn 作为更抗钓鱼的第二因素，但不把它作为首期设备前提；策略切换须由安全管理员强化验证，不能静默降级。单人发布减少操作等待，但不提供第二个人发现误操作或恶意行为的保障。

| 动作 | 强化验证 | 其他条件 |
|---|---|---|
| 查看已授权范围的列表、脱敏指标 | 普通有效会话 | 服务端范围校验 |
| 上传前创建许可 | 操作密码 + TOTP；未来可用 WebAuthn | 许可绑定预声明摘要、大小、分组、插件和环境 |
| 发布生产版本 | 操作密码 + TOTP；未来可用 WebAuthn | 同一授权用户确认精确计划，自动门禁通过 |
| 开始灰度、人工放量、全量、回滚 | 每个动作重新强化验证 | 当前动作授权、最新基础修订、目标仍可信 |
| 撤销制品、修改信任 / 安全策略 | 操作密码 + TOTP；未来可用 WebAuthn | 单名具有专门权限的管理员或预设应急规程 |
| 自动停止放量 / 回滚 | 不模拟人工密码或验证码 | 仅执行预授权计划中的安全收缩动作，完整审计 |

图形验证码只是反自动化手段，不是第二因素。生产不将短信 / 邮箱验证码作为默认高权限发布因素。

### 7.2 凭据管理

- 操作密码仅保存现代慢哈希及盐，建议 Argon2id，参数按服务器压测配置；可使用独立 pepper 并由外部密钥服务管理。不得保存明文或可解密操作密码。
- 建议最低 12 字符并校验常见泄露口令，不要求容易诱导弱口令的固定字符排列规则；设置与更改时拒绝与当前登录密码相同。
- TOTP 种子必须可用于验码，因此采用加密存储并由外部密钥保护，不能声称可以仅存哈希；只有绑定时一次展示，日志、埋点、截图采集禁止包含种子和二维码。
- TOTP 使用成熟标准实现，限制时间窗口（建议当前步及相邻一步），按账号 / 因素记录已消费时间步并原子防重放；下一敏感动作可能需要等待下一验证码。多实例共享该状态，不能只放本机内存。
- WebAuthn 校验 RP ID、Origin、challenge、凭据归属与用户验证要求；需要时直接在独立可信授权站点显示计划并完成验证，降低主业务页面被篡改的影响。WebAuthn 不能保证受控终端显示的内容真实。
- 首次绑定、替换、丢失恢复和删除因素须执行独立身份核验；不能只凭已有登录会话重新绑定攻击者的因素。
- 恢复码单次使用且仅存哈希。MFA / 操作密码恢复后撤销相关会话和未用授权，记录并通知账号本人和审计方；未完成新因素绑定和重新验证前禁止发布。无恢复码时由预置受控运维身份或有恢复权限的一名安全管理员核验身份，不把此过程改成日常双人发布审批，也不允许仅凭被盗会话重绑。
- 认证失败按账号、来源和动作联合限流，递增退避，避免无限重试；防止仅靠恶意失败请求长期锁死整个发布平台。
- 密码、OTP、恢复码、Bearer、挑战响应和完整授权票据不进入应用日志、APM 请求体或浏览器分析事件。

## 8. 动作绑定授权，避免“验证过一次就可随便发布”

### 8.1 挑战与授权载荷

服务器先从当前资源状态生成规范化动作意图，并计算摘要。挑战绑定：操作人、会话标识、账号与因素版本、动作、分组及归属修订、资源标识、环境、制品摘要或发布组版本向量、配置 / 灰度策略摘要、预期基础修订、随机 nonce 和有效期。

强化验证成功后签发只能执行该动作的一次性授权，不返回长期 `verified=true` 状态，不授予数分钟内任意敏感动作的通行权。

建议起始参数：挑战有效期 2 分钟，动作授权有效期 60 秒；成功消费后不可重用。长构建和长预热执行的是已受理的持久任务，不要求 OTP 在整个任务期间一直有效。参数可调整，但不得通过普通业务参数降低生产安全底线。

### 8.2 上传前验证与最终字节绑定

1. 浏览器对选中文件计算摘要，声明文件大小、插件 ID 和目标范围；该声明只是约束，不是服务器的验证结果。
2. 服务端创建挑战，用户完成操作密码及第二因素验证。
3. 单次消费动作授权并创建限时上传会话，建议上传会话有效期 15 分钟，约束总大小、分片、摘要和隔离位置。
4. 文件流入隔离区，服务器独立计算完整摘要；不匹配立即失败，不构建、不签名、不加载。
5. 上传会话允许受控续传；完成操作幂等，相同上传不能产生多个有效制品任务。超时会话不可借旧认证不断延长。

这样既在上传前完成验证，也防止验证后悄悄更换实际文件。JAR 大小上限独立配置，不能直接复用现有普通附件上限而不评估展开风险。

### 8.3 原子消费、重试与撤销

- 执行动作时再次校验有效会话、未锁屏状态、当前角色和分组范围、凭据 / MFA 版本、策略门禁、计划状态和资源修订。
- 授权消费与“动作已受理”记录在授权系统内原子完成，防止并发重复使用。跨系统通过持久动作 ID、幂等命令和状态查询协调，不假装多个服务共享一个数据库事务。
- 请求超时后按动作 ID 查询；不能重放授权或盲目重新发布。相同幂等键但不同动作摘要应拒绝。
- 发布修订更新使用条件更新 / 等效并发控制。操作人看到的基础版本已变更时，重新展示差异并授权，不覆盖别人刚发布的策略。
- 退出登录、锁屏、禁用账号、撤销角色、修改凭据、重绑 MFA、取消计划及插件移组均使相关未用授权失效。
- 对已经受理的长任务，在开始加载和激活两个关键阶段重新检查撤销状态；授权失效不应让已上传的隔离文件自动执行。
- 采用 Bearer 的现有 API 要防 XSS 和令牌泄露；若引入 Cookie 认证则同时完善 CSRF。限制 CORS / Origin 只是补充，不能替代身份和授权校验。

## 9. 制品、发布签名与密钥治理

制品记录包括源文件摘要（存在源码时）、构建工具链、锁定依赖、SBOM（依赖组成清单）、扫描结果、契约测试结果、入口清单、SDK 范围、生成物摘要、证明身份及时间。

当前没有企业 CI，支持两条显式标记的接入路径：源码由平台隔离构建，生成“平台构建证明”；开发人员本地构建的 JAR 通过上传者身份、文件摘要、依赖 / 字节码校验、扫描与隔离契约测试后，生成“导入验证证明”。后者不虚称已验证源码来源或可复现构建，更不能通过测试推断没有恶意代码；只有用户在其授权范围再次完成发布验证后才可执行。所有生产插件的团队规范均要求保留可获得的源码提交标识及构建资料，缺失来源信息必须显式标识。

发布清单至少绑定：制品及依赖摘要、分组及归属修订、插件 ID / 实现版本、目标应用和环境、业务契约 / API 契约、配置摘要、灰度策略、发布计划 ID、操作人及强化验证证据引用、节点目标范围、单调递增发布修订、前置修订、签名 keyId 和撤销引用。不包含密码、验证码或完整认证秘密。

密钥治理要求：

- 制品构建 / 导入证明与发布授权使用分离的密钥、签名用途及服务身份；生产与测试分开。首期共用安全服务并不等于两个独立受保护的硬件信任域，其失陷影响必须如实评估。
- 当前没有 KMS / HSM，按 4.3 在安全节点使用受控软件密钥存储，未来可替换为 KMS / HSM。业务服务只能请求其已有权限内的动作，不能提交任意摘要直接获得签名。
- 轮换保留必要的旧公钥验证历史证据，但历史可验签不代表仍有执行资格。
- 撤销区分单制品、单发布、单签名密钥及整个节点；明确对在途请求、后续流量和已加载实例的处理。
- 不能允许数据库恢复、服务重启或重放旧清单把修订倒退。正常回滚签发一个新的更高修订，指向仍可信的旧制品。
- 发布授权使用明确的签名用途和环境隔离，不能把测试签名、上传票据或制品证明当成生产执行许可。

### 9.1 用文件哈希验证一致性

可以并且应使用 SHA-256 检查字节是否一致。哈希是一份文件的内容指纹：改名不改变哈希，修改内容、重新打包或更改包内时间戳都可能改变哈希。实际签名绑定最终交付字节，签名后不得重新打包；不用 MD5 / SHA-1 作为安全完整性依据。

| 阶段 | 比较 / 绑定什么 | 失败时的处理 |
|---|---|---|
| 用户选择文件后、上传前 | 浏览器分块计算 H1，上传挑战绑定 H1、大小、分组、插件和环境 | 重新选文件须创建新意图并验证 |
| 上传完成 | 服务端对实际接收的完整字节计算 H2，要求 H2 = H1 | 丢弃有效性标记，隔离文件，不进入构建 / 验证队列 |
| Java 编译或合法构建转换后 | 源码哈希与输出 JAR 哈希分别保存，签署来源映射、工具链和依赖记录 | 不要求源码哈希等于 JAR 哈希；构建失败不能发布 |
| 已有 JAR 直接导入 | 验证通过后的原始完整 JAR 摘要仍为 H2；扫描不悄悄改包 | 如必须转换，生成新制品哈希并明确来源关系 |
| 发布验证 | 页面展示最终 JAR 摘要 H3，操作授权和签名清单绑定 H3；多 JAR 绑定全部摘要及版本向量 | 上传授权不替代对最终制品的发布授权 |
| 下载及主进程加载前 | 对不可变本地快照重算 H4，要求与签名清单 H3 相同，并验签、校验环境 / 修订 / 撤销状态 | 不定义类，不接流量，记录告警 |
| 存储巡检与重启恢复 | 检查制品、私有依赖和清单，恢复时重新验证执行资格 | 发现变化隔离，不重新计算哈希后自动视为新合法版本 |

分片校验只负责传输块，不代替完整文件哈希。多 JAR 发布组使用规范化有序清单记录每项 ID、版本、字节数和完整摘要，再对清单签名；不能依赖 ZIP 文件名或把各哈希随意连接成有歧义字符串。

哈希解决“是否是同一份内容”，不解决“谁允许它运行”。攻击者若同时替换 JAR 和普通数据库中的哈希值，纯哈希比较仍会通过；把预期哈希放入独立安全服务签署的发布清单，并由宿主使用受信公钥校验，才能约束正常加载路径的来源和授权。HTTPS、文件 ACL、一次性动作授权和不可变存储仍需保留。

哈希相同也不代表内容安全：恶意文件同样有正确哈希；在用户选择之前已被篡改的文件，会从第一步起就产生恶意文件自己的正确哈希。来源追踪、技术检查、明确展示和用户发布授权解决不同问题。宿主已经完全失陷时，攻击者还可能绕过所有比较，仍按第 3 节处理。

## 10. 插件 SDK、ClassLoader 与宿主能力

- 每个插件版本拥有独立 ClassLoader、实例及生命周期；同一逻辑插件的版本 ID 与运行实例 ID 分开。
- JDK、SDK、公共 DTO 和必要框架类型由父加载器提供；插件私有依赖采用受控隔离策略。禁止覆盖宿主包、公共 SDK 和框架核心类型。
- 共享 SDK 保持小且稳定，只暴露处理器契约、不可变请求上下文、受控能力接口和结果类型，不暴露 ApplicationContext、BeanFactory、DataSource、任意 ClassLoader 或通用反射入口。
- 首期使用普通 Java 处理器，构造注入明确能力；如未来需要插件 Spring 容器，必须验证方法安全、事务代理、销毁回调及缓存释放，不向宿主根容器随意注册版本 Bean。
- 不把 DTO 中的插件私有类、异常对象和缓存值长期保存在宿主。跨边界对象使用公共契约并限制大小和序列化深度。
- 宿主能力适配器继续校验认证上下文、租户、数据范围和允许操作；禁止插件自行声明 tenantId 绕过校验。但同 JVM 恶意代码仍可能绕过 SDK，这属于部署信任假设。
- 插件不能自行创建不可追踪线程、全局监听器或定时任务；受管理异步任务继承并最终清理可信上下文与版本引用。
- 可评估 PF4J 作为加载器基础，但它不自动提供双版本灰度、发布安全或可靠卸载。兼容 Boot 4 / Jackson 3、同逻辑插件多版本并存和类加载行为必须做专项验证。

## 11. 业务模块、版本与灰度模型

### 11.1 多种业务入口接入

已有 API 保留原 URL 和 Controller，由稳定入口委托指定业务处理器；新增接口通过保留命名空间及动态接口目录管理。管理接口与开放应用接口分别进入原有安全链。

接口目录声明 apiId、HTTP 方法 / 路径、契约、身份类型、权限或应用能力范围、输入限制、审计动作和所有者。动态业务权限不能从上传代码自行授予调用者；先登记并经过独立授权流程。

保留认证、密钥、发布管理、Actuator 等核心路由，不允许插件覆盖。相同路由冲突应在发布前拒绝。动态接口请求体、序列化和文件处理限制与普通 API 同样生效。

| 入口 | 稳定宿主适配层 | 热更新的实现 |
|---|---|---|
| HTTP API | 现有 Controller / 动态接口目录 | 接口业务处理、协议转换 |
| 内部业务服务 | 稳定 Java 接口 + 版本分发代理 | 业务计算、转换、规则与编排 |
| 事件 / 消息 | 宿主长期持有的消费者与事件适配器 | 指定契约的事件处理逻辑 |
| 定时 / 批处理 | 宿主调度器与任务登记表 | 批量数据处理、周期性业务任务逻辑 |

业务模块可由多个处理器、策略、资源文件和私有依赖组成，不局限于一个 Java 类或一个 API。调用链通过稳定 SPI 获取指定版本，不把实现 Bean 直接注入所有调用方，否则宿主调用方可能永久持有旧实现。

插件声明能力 ID、契约版本、入口种类、依赖能力和状态兼容范围。宿主在加载时建立明确注册表，不重新扫描整个应用或任意刷新根 ApplicationContext。核心认证和发布管理不注册为可替换扩展点。

### 11.2 三种版本

| 标识 | 说明 |
|---|---|
| 业务契约版本 | Java 服务接口、API、事件与任务输入输出的兼容性 |
| 插件实现版本 + 制品摘要 | 精确执行代码，不允许同版本覆盖 |
| 发布修订 | 哪些版本在什么配置和灰度规则下接收流量；每次变化递增 |

关联业务插件可组成发布组，例如“插件 A 2.1 + 插件 B 3.0”；入口固定兼容版本向量。所有成员准备就绪后一次切换本机业务入口快照，任一失败则不激活整组。插件不能通过缓存私有实现绕过快照重新分派。配置、规则文件和模型资源同样版本化并绑定发布；密钥配置只引用外部秘密版本，不写明文。

### 11.3 灰度规则

优先级建议：受控测试名单 → 租户 / 应用白名单 → 稳定散列分桶 → 稳定版本。身份来自服务端认证上下文，不接受调用者任意指定版本或租户请求头。

在同一发布周期固定分桶盐、算法和身份键；按租户分桶适合租户整体一致，按用户 / 应用分桶适合细粒度试运行。桶比例不保证等于实际流量比例。

请求一开始固定版本和路由修订，执行中不再重选。跨请求业务流程、幂等操作、异步任务、消息和重试按语义保存并传递执行版本或发布组，避免处理同一业务事实时随机跨版。

灰度缓存需按租户、必要的契约 / 实现版本划分。禁止默认对写 API 做双版本影子执行；只读影子验证也要隔离资源和敏感输出。

### 11.4 通用有状态业务与副作用控制

本节是可复用的扩展契约要求，不指派任何具体业务开发。无副作用转换、只读查询、有状态写入和长任务按各自契约接入，只有涉及持久状态 / 外部副作用的插件才承担对应要求。

- 有状态操作保存稳定业务标识、契约版本、实际插件及配置版本、必要输入依据和结果；敏感输入做最小化记录与访问保护。
- 同一业务使用稳定幂等键，不能因插件版本变化变成“新业务”。本地提交与结果记录尽量在同一事务完成，外部系统交互采用持久意图 / outbox、幂等请求与对账，不能声称跨系统天然恰好一次。
- 若插件产生需要后续使用的判定或计算结果，宿主检查其业务归属、版本、有效期及撤销状态，不能信任客户端自行提供的成功标识。
- 同一长期业务流程在创建或首次受理时固定发布组，后续重试、消息和回调沿用；新灰度默认作用于新业务实例。纯无状态调用可按请求选版，无需为此建立业务数据库。
- 普通发布不会重算历史数据；重处理是单独任务，需要明确影响范围、差异、幂等及补偿，不能用回滚按钮代替。
- 紧急撤销不在事务中途强换实现。原版本不再可信时隔离相关工作，由可信恢复流程决定后续处理，安全阻断可优先于版本黏性。
- 新版按插件契约使用固定样本验证输出、错误、耗时和资源变化；影子执行默认只允许无副作用评估，不能重复写库、发通知或调用外部写接口。
- 超时及故障返回契约定义的处理中、失败或暂不可用，不伪造成功或绕过权限；不强杀提交中的线程。

### 11.5 事件、定时任务与持久状态

- 消息消费者和调度器由宿主持有，禁止新旧插件各自注册一套消费 / 定时执行而双重处理。
- 与已有业务关联的事件使用该业务已固定版本；无既有版本的事件由宿主在首次受理事务中确定并持久保存，之后重投沿用。由宿主产生的事件可在入队时绑定版本，消费者只采用可验证的内部元数据。
- 定时任务在建立运行记录时固定版本与配置；同一任务实例有唯一幂等标识，重试不改成新版本。跨节点使用租约、唯一约束与 fencing token 防止过期执行者继续提交。
- 不承诺消息系统绝对只投递一次。通过原子受理记录、幂等提交、受控重试及必要的 outbox 保证业务结果；不能只用内存锁。
- 插件状态优先外置到所属业务模块的版本化持久结构。不给新旧插件共享未版本化可变静态变量，禁止偷偷把旧实例内存拷贝到新实例视为完成迁移。
- 对长期业务实例、重试任务和事件，仅“当前在途请求为零”不足以卸载。宿主维护持久版本引用和保留策略；没有可执行引用或已完成明确的兼容迁移后才能停用 / 回收。
- 同时保持多个历史业务版本会消耗资源。达到驻留版本预算时阻止新发布或先完成业务收尾，不能强制淘汰仍被业务实例 / 消息引用的版本。已停止版本重新加载也需当前有效授权。

## 12. 发布、回滚、排空与故障处理

生命周期：隔离上传 → 已验证 → 已签名 → 发布人动作验证通过 → 准备加载 → 已就绪 → 灰度 → 全量 → 排空 / 等待业务引用结束 → 已停止。失败与撤销分别有独立状态，不以“删除一行记录”代替撤销；没有等待第二人审批的状态。

加载前验证不通过时不定义插件类；初始化失败时保持现有路由，释放已分配资源。预热不允许自动写生产数据或发送真实业务消息。

本机路由以不可变快照原子切换。旧版排空等待同步请求、异步任务、流式响应及受管理后台工作完成，并检查持久业务引用；超时不能用强杀线程保证安全，应按业务策略拒绝新任务、告警或隔离整个执行节点。涉及副作用的切换以业务受理和提交边界为准，不在事务中途换实现。

回滚只改变后续执行的代码 / 配置，不撤销已提交数据库数据、发出的通知或第三方操作。写操作不能在新版超时后自动换旧版重做，必须依赖幂等键及持久执行结果确认。

释放实例、清理线程本地变量 / 缓存 / 监听器并关闭加载器后，仍需 GC 才可能回收类。签名可信也不保证无泄漏；持续泄漏或宿主不可恢复时，应允许维护重启。免重启是正常发布目标，不是事故处置限制。

### 12.1 控制面故障与重启恢复

稳定性与安全性优先，具体落实为“停止不确定的新变更；受控保留最后可信版本；不破坏正在提交的业务；无法证明安全时停止受影响业务”。不承诺网络分区期间既无限服务又立即获知所有撤销。

| 故障 | 新发布 / 加载 | 已运行业务 |
|---|---|---|
| 新版校验、构建、预热失败 | 拒绝本次发布 | 旧版继续，不为修复发布故障自动重启宿主 |
| 安全服务、签名或关键发布审计短暂不可用 | 冻结上传授权、加载、放量、信任变更 | 在尚有效运行租约内使用最后可信版本，不让每次业务调用依赖控制面往返 |
| 运行租约过期且无法续租 | 拒绝新增执行资格 | 拒绝新的插件工作；正在执行的事务按预设边界完成或正常回滚，不强杀线程 |
| 已确认制品篡改 / 撤销 / 节点失陷 | 阻断相关执行 | 隔离受影响能力或节点，不伪造业务成功或跳过校验，转受控恢复 |
| 宿主重启且控制面不可用 | 不加载插件 | 静态业务按依赖关系继续或标记不可用；不从主库单方面恢复执行 |
| 资源压力过高或版本无法排空 | 暂停新发布，限制新任务 | 保护稳定业务，保留必要版本，告警处理；不用释放仍有引用的类加载器换取容量 |

建议运行租约初值 15 分钟、每分钟提前续租，配合抖动和有界退避；这些是待压测 / 演练确定的建议，不是用户已确认参数。租约绑定节点、环境、制品集合和当前修订，由安全服务签发并检查撤销；只依赖主库状态不算续租。时钟异常需拒绝新增授权，并用可信签发时间和单调计时约束本机有效时长，不能因系统时钟回拨无限延长。

断网时不能即时知道新的撤销，最大风险窗口由剩余租约约束。缩短租约提高撤销及时性，但增加控制面故障对业务的影响；首期不设置无限离线宽限。运行租约决定是否接收新的工作，不自动中断已经受理的事务，也不允许已受理的一个长任务无限派生新的工作。

租约到期或节点不可用时，消息不被错误确认，批任务暂停领取；业务按契约返回处理中、失败或不可用，需要延后处理的工作进入有界持久队列，不默认成功。恢复后核验当前可信修订与幂等结果再续处理，避免补偿时跨版重复执行。

重启恢复必须从安全服务获取当前修订和有效执行资格，核验制品快照；一次性动作授权、发布计划有效期与运行租约分别管理。首期不设计无授权的离线冷启动。安全服务的备份恢复、密钥备份及故障演练是生产前置要求；按实际可用性要求增加冗余，单个安全节点不应被描述成高可用架构。

### 12.2 多节点扩展

先分发并取得目标节点的制品 / 配置就绪回执，再激活发布修订。数据库条件更新和控制面租约防并发发布；消息通知只作加速，节点按持久修订对账。

每节点原子切换不等于全局瞬时一致。要求严格一致时，由可信入口固定发布修订并只向具备该修订的节点路由；不可用节点移出目标池。扩容节点满足同样验证及就绪规则后才能接流量。

## 13. 事务、事件与数据库兼容

- 事务由宿主服务或显式受控事务能力承担；插件上的任意注解不默认被 Spring 代理处理。
- 保持现有跨模块事件约定，使用宿主稳定事件类型 / 版本化消息封装；不要持久化只能由已卸载插件反序列化的类型。
- 异步消息至少有事件标识、可信租户、契约 / 处理版本语义及幂等信息。重投不能无条件改用“最新版本”。
- 插件不得直接读写其他模块表。确需新增数据能力时，先通过正式模块设计与 Flyway 发布。
- 数据库采用扩展—迁移—收缩策略，新旧版本并行期间兼容双方；删除字段、改变含义和不可逆迁移与普通热更新分离。
- 预先检查回滚目标是否能读取当前数据、事件和缓存；不兼容时禁止把代码回滚按钮描述成可安全恢复业务。

## 14. 模块落点与数据归属

| 位置 | 职责 |
|---|---|
| `extension` 新模块 | JAR 分组及权威目录投影、制品元数据、能力 / 接口目录、发布组、发布计划、节点执行记录、运行时与管理 API；表前缀 `extension_` |
| `common` 新命名接口 | 最小插件 SPI、稳定 DTO、受控能力贡献契约；不依赖 extension |
| `auth` | 登录会话联动、强化认证接入、凭据 / 因素撤销语义；本地流程不能替独立控制面伪造认证证明 |
| `iam` | 普通权限展示、授权目录及平台角色映射；关键发布权由外部可信目录复核 |
| `audit` | 接收稳定审计事件和查询本地投影；外部不可变审计保存关键证据 |
| `monitor` | 通过公共查询契约展示插件版本、流量与节点状态，不越界读 extension 表 |
| 现有业务模块 | 通过 common 中的能力契约贡献适配器，保持数据和事务所有权 |
| 最小发布安全服务及隔离构建器 | 分组归属 / 权限、关键认证、动作授权、签名与审计的权威来源；从零建设，不放在插件可调用的宿主能力中 |

普通文件模块可复用有限元数据工具，但可执行制品必须有独立隔离区、配额和访问策略，不能复用“上传完成即公开下载 / 可执行”的语义。

本地建议记录以下概念，不在本方案中实现表结构：分组及授权投影、插件目录、制品及验证记录、业务契约、发布组版本向量、发布计划和动作状态投影、发布修订、节点部署、路由策略、版本引用、执行指标与审计关联。业务版本固定与幂等记录由所属业务模块持有，运行时只通过明确契约查询保留引用。授权挑战、单次消费、关键授权和分组归属的权威记录由安全服务持有，不建立审批表来代替已取消的双人流程。

平台发布记录不伪装成某一普通租户的业务记录；需要明确平台级资源上下文和数据访问规则。现有租户过滤例外仅允许 OpenAPI 凭据启动查询，不能为方便增加任意跳过租户的注解。相关架构规则应在后续实施时经评审精确扩展，并保持普通租户不可访问。

## 15. 版本发布管理界面

### 15.1 页面范围

| 页面 | 主要内容与操作 |
|---|---|
| JAR 分组 / 插件目录 | 分组树或分组列表，组内插件、入口类型、所有者、环境、当前版本、允许宿主能力 |
| 制品版本 | 上传、摘要、来源证明、验证失败原因、签名 / 撤销状态、兼容范围 |
| 发布计划 | 新旧差异、目标环境、灰度名单与比例、配置、观察指标、回滚目标 |
| 我的操作 / 发布任务 | 验证待完成、校验中、待加载、灰度中、失败、已完成；精确动作、发起人、原因和重试查询，无待审批页 |
| 运行状态 | 节点就绪、每版请求 / 错误 / 延迟、当前修订、在途任务、排空情况 |
| 安全与审计 | 权限范围、因素状态、失败验证、撤销、信任变更与审计关联 |

### 15.2 上传与发布交互

- 上传：选择分组和插件 → 选文件并计算哈希 → 显示名称、大小、摘要和范围 → 操作密码及第二因素 → 接收隔离上传 → 显示一致性及技术验证结果。未验证不开始发送文件内容。
- 发布：选择组内插件 / 发布组 → 展示环境、最终制品哈希、版本 / 配置差异、业务能力及 API、灰度范围和回滚条件 → 自动门禁检查 → 同一用户本次操作验证 → 显示持久动作 ID → 跟踪加载、就绪和生效，不等待他人审批。
- 输入认证信息后若改变制品、环境或策略，已取得授权失效，界面必须重新验证。
- 防连点由按钮状态和服务端幂等共同保证。网络断开后显示“状态待确认”并查询，不显示未经确认的成功或再次提交。
- 不具备权限时不给可操作入口，直连接口仍由服务端拒绝。显示未获授权的原因时避免泄露无权查看的插件和环境信息。
- 确认对话框默认不预选“全量”；生产环境显著标识。升级验证字段不写入 localStorage、URL、持久草稿或埋点。
- 页面沿用项目中英文及用户时区约定；审计底层存 UTC。暂不制作页面代码或交互原型。

### 15.3 分组视图与哈希展示

分组由平台管理员按实际项目创建，不内置示例业务分组。组内按插件查看版本，支持环境、状态、上传人和时间过滤；同一插件跨环境版本并排可查。普通列表显示哈希短摘要便于识别，详情和确认页提供完整 SHA-256 及复制能力，实际校验始终使用完整值。

批量上传可一次验证绑定精确文件清单，各文件独立报告成功 / 失败；文件列表变化重新验证。批量发布必须声明“独立任务”或“协同发布组”，前者显示逐项结果，后者先全部就绪再激活，不能部分成功却显示整组发布成功。首期默认逐插件发布，协同业务明确创建发布组。

首期默认展示通用指标：调用量、错误率、P95 耗时、超时、排队量、在途工作、版本引用、发布状态及宿主资源压力。预留插件贡献受控业务指标的接口，后续随实际业务接入，不预建领域专用报表，也不将通用成功率等同于业务正确性。

## 16. 审计、监控与服务器失陷响应

每个重要事件记录：实际操作者及工作负载身份、动作 ID、会话关联、认证因素类型（不含秘密）、分组及归属修订、环境 / 目标范围、制品摘要、配置和策略摘要、用户确认及动作授权证据引用、修订前后值、节点、结果、错误类别与 UTC 时间。不记录不存在的“第二批准人”。

敏感发布动作先在独立控制面形成持久记录才可受理；无法记录时拒绝新的高风险动作。普通请求审计可异步缓冲，但必须有容量、丢失告警和保留策略。仅在本机做哈希链不能抵抗能重写整条链的攻击者，应外送至追加写 / WORM 或等效独立保护存储。

监控未授权加载尝试、验签失败、摘要变化、修订倒退、MFA 重放、大量验证失败、角色 / 因素重置、异常 agent 参数、进程调试、执行目录修改、插件线程和内存增长。检测是补充证据，不承诺识别所有内存攻击。

发现主进程 RCE 或服务器管理员失陷时：

1. 从外部网关 / 负载均衡移除节点，阻断其访问密钥、制品和发布控制面；不能只依赖被入侵进程中的禁用开关。
2. 撤销节点身份、运行租约及可能暴露的服务凭据，冻结相关发布并保全外部证据。
3. 排查来源和影响面，按暴露范围轮换数据库 / 应用密钥；不能仅删除可疑 JAR 后继续认为宿主可信。
4. 从可信镜像 / 安装包重建节点，修复入口漏洞，重新拉取并校验获授权制品。
5. 完成完整性和业务验证后恢复流量。事故期间可重启或停机，安全处置优先于免重启目标。

应急权限不能是隐藏免验口令。首期准备安全服务独立账号、受保护的一次性恢复材料、限时最小权限及告警；有条件再增加硬件认证。具有应急权限的一名人员按既定恢复验证执行，不额外要求双人发布审批；自动控制器可预授权停止新流量或回滚到指定可信目标，不能加载未知新代码。

## 17. 分阶段实施建议

| 阶段 | 交付目标 | 退出条件 |
|---|---|---|
| A：契约与最小安全底座 | 从零建设发布安全服务、TOTP、软件密钥、私有制品区、审计与隔离验证；定义 HTTP / 内部服务 / 事件 / 任务通用扩展点和分组权限 | 单名有权用户能通过验证完成动作，越权及未验证代码不能进入正常加载路径 |
| B：单实例 JAR 闭环 | 分组管理、文件哈希、无副作用转换样例、双版本、灰度、回滚、排空、重启恢复 | 宿主进程不变；不要求第二人；哈希替换、状态恢复和资源验证通过 |
| C：状态契约与源码上传 | 隔离测试存储中的幂等写入样例、事件 / 任务、持久版本引用、发布组、隔离源码构建 | 无跨版重复副作用；构建隔离和数据兼容通过，不新增真实领域业务 |
| D：运行保障与多节点 | 备份恢复与入侵演练、控制面故障策略、共享防重放、分发协调、入口修订固定 | 故障时明确保留 / 暂停边界；生产单实例也完成相应备份与故障演练 |

阶段 A 的签名、授权、MFA 和审计不是生产上线后再补的选配功能。业务插件首期统一同 JVM，不排入独立业务执行器建设；如果未来改变该决定，需要另行评估调用、事务及故障边界。样例仅验证通用底座，不构成新的业务建设需求。

## 19. 通用资源与安全策略：首版默认设计

本节按用户授权确定首版默认规则，用于后续实现，不再作为需要用户逐项选择的问题。默认值偏向中小型内部 Java 扩展，属于产品基线而非已测得的最佳容量；上线前验证边界和资源，后续允许有权限的管理员通过策略修订调整。

### 19.1 文件、存储与版本配额

| 项目 | 首版默认值 | 达到限制时 |
|---|---|---|
| 单个插件 JAR | 100 MiB；依赖另附时同样逐文件校验 | 上传许可即拒绝超限文件，不能拆片绕过 |
| 一次上传的完整插件包 / 批次 | 300 MiB、最多 20 个文件；含私有依赖与资源 | 服务端按清单预占配额，超过任一限制拒绝 |
| Java 源码 | 单文件 1 MiB、单批 10 MiB，仍受 20 文件限制 | 拒绝超限，复杂工程走固定构建流程产生 JAR |
| 单个插件包累计展开 | 500 MiB、20,000 个条目、最多 2 层显式声明的嵌套依赖归档 | 解析时流式累计，触线即停止，不能每层重新计算额度 |
| 压缩比与解析时限 | 总体及单条目压缩比不超过 200:1；隔离元数据 / 解包校验最长 60 秒 | 拒绝异常包；构建和漏洞扫描使用各自任务时限 |
| 单插件 / 单分组仓库存储 | 2 GiB / 5 GiB | 停止新增，显示占用来源和可清理项，不移除在用制品 |
| 单制品仓库总预算 | 20 GiB，测试与生产共仓时合并计数 | 达到上限拒绝新增，禁止靠新建分组绕过 |
| 磁盘剩余空间保护 | 写入 / 展开后至少保留该卷容量 10% 与 5 GiB 中较大值 | 暂停上传和构建；小磁盘不满足时明确阻止，不偷偷降低门槛 |
| 历史版本保留 | 保留最近 20 个未引用版本及最近 30 天的版本，取并集；另外保护所有在用、回滚、业务引用和依法保留版本 | 保留要求超出配额时拒绝新增，提示扩容或清理非保护版本 |
| 同插件 / 同宿主的驻留版本预算 | 默认 3 个：稳定、灰度、排空；所有有引用的其他旧版同样占预算 | 第 4 个版本加载前阻止发布，先收尾或经容量验证上调预算 |

MiB / GiB 使用二进制计量。仓库逻辑配额按每个插件版本引用的完整制品及私有依赖计量，去重不增加用户额度；物理磁盘另行监控。多环境指向同一不可变版本不重复占逻辑配额，克隆新版本则重新计量。暂存上传、未完成分片、解包和构建工作区单独计量并共同受磁盘剩余空间保护，不能作为无限存储后门。

配额检查使用原子预占，上传取消 / 超时释放占用；接收后按真实大小复核。无引用的失败 / 过期上传字节保留最长 24 小时用于短期排错，然后由受控清理任务清除；已确认恶意包隔离并默认删除可执行字节，保留哈希及失败证据。生产制品清理先展示清单，具备清理权限的用户验证后执行，不因“旧版本”自动物理删除；安全审计元数据独立保留。未获得配额不能接受字节后再无限排队。

### 19.2 构建与发布资源保护

- 单环境同时最多 1 个激活 / 路由变更任务，包含发布、放量、回滚和会影响路由的撤销；紧急撤销优先调度，并在每个激活步骤重查撤销状态，不能因普通发布占队列延后安全阻断。
- 单构建节点默认最多 2 个隔离构建 / 扫描工作，等待队列最多 20 个；超出返回明确繁忙结果，不创建无界线程或内存队列。
- 每个隔离构建工作默认上限 2 vCPU、2 GiB 内存、2 GiB 工作区和 10 分钟执行时间；漏洞扫描同样有界，单次最长 10 分钟。上限由操作系统 / 隔离执行环境实现，未具备限制能力时不能声称已隔离。
- 发布前检查最近 5 分钟的宿主资源；堆占用或配置了上限的 Metaspace 占用达到 80%、CPU 持续高于 80%、指标不可用或构建节点空间不足时，暂停新加载并保留稳定路由。Metaspace 未设上限时不能伪造百分比，应使用经部署设定的绝对预算及趋势门槛。
- 这些门槛只决定是否接纳新版本，不证明剩余空间一定够用；加载前还检查预热测得的新增开销，并保留额外余量。没有可用容量评估的插件不得直接全量。
- 同 JVM 插件不能得到可靠独立堆限额或强制 CPU 隔离；业务调用的超时不保证其底层执行停止。长任务由宿主受控执行、限并发并支持协作取消，出现泄漏时暂停新发布并按故障规程处理。

### 19.3 依赖白名单

白名单控制“允许哪些库随插件使用”，不控制任意 Java 代码的所有行为。首版按以下分类执行：

| 依赖类别 | 首版规则 |
|---|---|
| JDK 与插件 SDK | 使用目标 Java 21 及兼容 SDK，SDK 由父加载器唯一提供；禁止插件自带替代副本 |
| 宿主显式共享库 | 仅开放公共契约真正需要的库和接口；版本以宿主已锁定 BOM / SDK 清单为准，不开放整个应用 classpath |
| 私有纯 Java 工具库 | 可登记成熟的纯计算、集合、编码等依赖；必须明确 groupId、artifactId、精确 version、SHA-256、来源和完整传递依赖，经验证后列入允许清单 |
| Spring / Boot、Servlet、Jackson 等平台核心类型及日志实现 | 不允许随插件覆盖、重复打包或通过 shade 隐藏后绕过；如契约需要使用，由宿主显式导出兼容接口；首期不引入私有框架栈 |
| 驱动、连接池、云凭据链、动态脚本执行器及进程工具 | 默认不开放，需要此类操作时通过明确宿主能力接入，不为插件提供通用系统访问工具 |
| Java Agent、JNI / 本地二进制、自定义运行时下载器及未经授权注解处理器 | 默认拒绝，首期不提供例外入口 |
| 未知来源、无法识别的嵌套依赖或缺失传递依赖清单 | 拒绝发布，先补齐来源、内容和兼容验证 |

不在文档中随意填入未经验证的第三方库版本号。初始白名单由实现时已验证的宿主 BOM 与最小 SDK 自动生成；其他依赖从空集合开始，由具备依赖管理权限的一名管理员强化验证后登记确切版本和摘要，再执行扫描及契约测试。同一用户可同时具有上传、发布和依赖管理权，但只拥有上传权不能扩大白名单。

禁止 SNAPSHOT、LATEST、RELEASE、版本范围和未锁定传递依赖。源码构建只经固定受控代理获取依赖，缓存按摘要保存；运行时不联网补包。SBOM 与实际 JAR / 嵌套包比对，不能只信任上传者声明；去除清单、重命名或重打包无法识别的库不能按“没有依赖”放行。

白名单只表示此版本可被评估，不自动覆盖漏洞门禁。依赖更新或替换摘要必须生成新制品并重新验证；不能因为同名库以前允许就接受任意新版本。

### 19.4 宿主能力默认范围

初始 SDK 只提供业务入口契约、不可变可信调用上下文、受控日志 / 指标及结果类型，不预置任何特定领域的查询或写命令。业务能力后续由实际所属模块注册，按插件、环境、身份和租户校验；新能力默认无授权。

默认不提供 ApplicationContext、DataSource、任意 SQL、任意文件系统、进程执行、通用网络客户端或密钥读取。需要 HTTP 调用时由宿主提供目标域名 / 方法 / 超时受限的能力；写操作须有幂等及审计契约。这是正常 SDK 路径的权限设计，不将同 JVM 恶意代码无法越界作为保证。

### 19.5 漏洞阻断与扫描时效

| 检查结果 | 首版处理 |
|---|---|
| 已知被利用且影响该制品的漏洞、恶意代码、已撤销组件 | 无论 CVSS 分值多少均阻断，不允许一般临时例外 |
| 严重 / 高危漏洞（CVSS ≥ 7.0，或可信供应商明确评级为高危及以上） | 默认阻断；仅能通过有证据的“不适用”或误报例外解除该特定告警 |
| 中危漏洞（4.0 ≤ CVSS < 7.0） | 展示告警及整改事项；不存在已知利用 / 其他硬阻断时允许发布，操作人确认页可见 |
| 低危漏洞（CVSS < 4.0） | 记录并持续跟踪，不单独阻断 |
| 严重程度未知、来源互相矛盾、组件无法映射、扫描失败或结果不完整 | 不按低危或“未检出”放行，暂停新发布，修复工具 / 数据或执行针对性复核 |

使用维护中的成熟扫描器和可信漏洞数据，首版每 6 小时尝试更新；新发布要求漏洞库最后一次成功同步不超过 24 小时，扫描结果不超过 24 小时。上线前在加载 / 激活关口重新检查扫描、撤销和策略修订；无法获取新数据时可用时效内缓存，缓存过期则冻结新发布，不自动卸载所有在运插件。

每 24 小时复查在运制品和已登记依赖，收到关键撤销信息立即复核。新增已确认可利用漏洞或恶意代码进入应急隔离；其他新增高危发现冻结该制品新发布并记录处置期限，不能因为旧扫描通过就永久续租。既有运行的收缩按风险和可信运行租约处理，保护在途提交，不能以“安全扫描更新”为由随机强杀线程。

无网络或目标平台无法运行扫描器时，生产发布检查必须显示不可用并拒绝，不以空结果代替完成。具体扫描器在实现时根据 Java 21、软件组成识别、更新渠道和部署条件选型，本方案不宣称现有环境已经具备扫描服务。

### 19.6 临时例外规则

- 默认没有例外。仅允许处理有证据的误报 / 不适用告警或已验证兼容事项，不允许“先上线再说”的无依据通行。
- 创建例外需要专门安全策略权限、操作密码及 TOTP；一名已授权管理员即可完成，不引入双人审批。保留原因、证据、责任人、整改目标和操作审计。
- 单次最长 7 天，精确绑定插件、制品 SHA-256、依赖 / 漏洞 ID、环境及策略修订；同组其他插件、新制品和其他环境不继承。
- 到期前 48 小时和 24 小时提醒；不足该时长的例外创建后提示。不自动续期，续期须重新验证依据、强化认证并生成新记录，历史不能被覆盖为“从未到期”。
- 无权限、未完成 MFA、签名失败、哈希不一致、已撤销制品、已知正在被利用且实际影响制品的漏洞、已确认可利用的代码执行漏洞或恶意代码均不可豁免。磁盘不足、依赖不明等也不能用“漏洞例外”绕过。
- 运行依赖某个例外时，租约截止时间不得晚于例外截止时间。例外到期阻止新发布 / 加载；到期前未修复或重新验证的版本停止接收新工作并进入正常排空，不突然强杀正在提交的事务。

### 19.7 后续优化与权限

上述规则存为有版本的策略，发布记录绑定其修订。普通上传者 / 发布者不能修改规则；具备 `extension:policy:manage` 的管理员单人强化验证后可修改配额、依赖规则和阈值，并展示影响范围、差异与原因，写入审计。分组停用、删除制品和清理空间仍遵守单独权限及引用保护。

配额提高不绕过磁盘和宿主健康检查；配额降低只阻止新的超额操作，不自动删除已有包。安全策略收紧重新评估存量并提供处置状态；策略变更不能让已撤销制品或验签失败包恢复合法，也不能静默关闭强认证。新策略发布前校验相互约束，如“单包上限大于总预算”应拒绝。

首版验收追加：并发上传不能超配额；展开 / 嵌套包不能绕过上限；受保护旧版本不能被清理；未锁定依赖不能通过；漏洞库过期冻结新发布；未知扫描结果不当作通过；临时例外不可跨哈希复用且按时失效；降配额不损坏现有执行。

## 20. 已确认决定与剩余实施输入

| 事项 | 当前结论 |
|---|---|
| 热更新范围 | 不限 API 的通用业务扩展底座；计费、风控只是例子，不列入业务开发范围；核心认证与发布管理默认不插件化 |
| 管理方式 | JAR 按业务分组，组内管理插件及版本；分组权限与协同发布组分开 |
| 现成基础设施 | 无；建设最小发布安全服务及配套隔离验证，不以已有企业平台为前提 |
| 操作流程 | 同一已授权用户验证后上传和发布，无双人审批 |
| 优先级 | 稳定性和安全性优先；冻结失败的新变更，保护可信业务，必要时停止受影响新工作 |
| 业务插件隔离 | 当前同 JVM；不建设业务独立执行器，但明确其安全边界 |
| 文件一致性 | 采用完整 SHA-256 校验链，并用签名清单绑定来源、权限及环境；构建前后摘要分别记录 |
| 通用策略参数 | 用户授权按一般情况设计，采用第 19 节首版默认规则，后续受控优化，无需逐项再次确认 |

后续真正需要的部署输入仅保留：生产操作系统与网络 / 节点条件、账号恢复责任及备份存放条件。底座可使用通用样例验证，不以指定实际业务为前提；实际模块将来接入时再定义其契约与数据边界。配额、依赖、漏洞门禁和例外期限按第 19 节实施并验证，不再次要求用户决定通用参数，也不把计费或风控作为等待补充的真实业务需求。
