# P08 部署配置与密钥一致性证据

属于已授权M3b2范围。实施状态以[P08进度](../cache-governance-progress.md)和[总排期](../development-schedule.md)为准；本方案本身不开放multi。

## 目标与边界

两实例访问同一持久账本只解决共享状态。认证加密/pepper、请求HMAC、租户凭据环、OpenAPI主密钥或缓存协议等配置不同，仍会造成随机失败。Common通过`common :: deployment`的宿主SPI收集各模块**实际使用对象**的证据，不读取他模块私有字段/表，不另建一份配置或密钥装载器。

证据仅供部署协调，不是登录凭据、用户缓存或HTTP接口。用户/匿名HTTP/tenant job/活动数据库事务均不能调用。模块归属依据真实类型及Modulith声明检查，不相信自行填写的owner。普通缓存清理不能触及它。

## 协议

每个部署清单代次持有一个随机256位挑战，绑定现有cluster hash和manifest hash；所有节点对同一挑战计算可比较的结果。挑战由Common后续持久协调器产生，不能由网页指定；最终写入仍绑定已有node/process/epoch租约，不建立第二套节点名册。

每个证据域使用固定协议版本、域名、部署、清单、挑战进行域隔离。密钥材料不离开所属服务的证据调用，不作为SPI返回值；对每把有效/保留密钥计算HMAC-SHA256，再按键ID排序，与活动键ID一起合成固定摘要。顺序不影响结果；同ID不同材料、丢失旧键或活动键变化均不能混用。缺少任何必需密钥即不可用，不能用空字符串冒充一致。

初始必需密钥域：`auth.security-keys`（加密环和pepper环）、`common.request-fingerprint`、`common.tenant-credentials`、`openapi.master-key`。未开启部署预检的单机保留原缺钥功能关闭语义。OpenAPI证据只读已明确配置的主密钥或已存在的文件，不建目录/新钥；当前进程自行生成的钥不授予部署资格。证据基于正在使用的对象快照，不以磁盘文件已改就声称运行密钥已更换。

配置证据使用逐模块白名单和确定编码：缓存provider/namespace/协议与区域目录/部署上限、Redis拓扑/逻辑DB/TLS、schema校验模式、认证会话策略、浏览器来源/预算、应用身份与消息策略及存储资源声明。不得对整个Environment、任意record或连接属性调用toString/序列化；口令、令牌、私有路径不进入输出。节点ID、进程ID、端口和本地挂载路径可不同；共享存储由M3b3实际互证，不能用配置摘要冒充物理共享证明。Redis ACL身份可按节点不同，连接可用性仍由受控连接工厂验证。

域数、字段数、字符串/密钥数均有上限，异常只报告固定域不可用，不暴露异常文本、原值或摘要于用户页面。域集合也进入总摘要，防止少装一个提供者仍通过。首次严格要求完整环及活动键一致；跨节点分阶段改钥不在此版本承诺中，须按清单换代与维护窗口协调，不能静默接受不兼容的滚动变更。

## 持久协调与资格

复用Common节点组/租约，由受信宿主短事务取得挑战、登记本进程证据及比较结果；计算/文件读取在事务外。只追加Common迁移，精确框架元数据例外，不允许业务复用免租户表。进程更替、租约失效、清单变化或挑战变化使旧证据失效。不能由不匹配节点覆盖已经接受的配置基线；显式代次变更沿用原清单单调与活租约保护。错误节点拒绝资格，已健康节点不能仅因错误peer出现就被拖下线。

本项产生配置资格，不等于流量就绪。M3b3再证明共享存储，M3c组合schema/租约/配置/存储/摘流，M3d经实际LB矩阵后才开放multi。不同数据库/恢复旧快照、真实网络分区与存储供应商HA不能仅由摘要证明。

## 实施与验收顺序

1. M3b2a：宿主SPI、有界确定性摘要/真实归属注册及四类运行密钥适配；测试顺序、域隔离、旧键缺失、同ID异值、缺钥、异常脱敏、HTTP/job/事务拒绝和OpenAPI不生成文件，并回归原加解密及请求消费者。
2. M3b2b：模块自有配置白名单适配，验证同义集合规范化和关键差异必改变摘要；真实宿主Bean收集验证必需域齐备且默认单机不触发预检。
3. M3b2c：追加持久证据、绑定既有租约和清单代次、工作线程及配置资格；真实MySQL竞争/替换/过期/错误节点隔离，再跑独立JVM不一致和一致配置矩阵。通过前不得宣称M3b2完成。

拟改路径：Common公开deployment及内部部署/协调存储，Auth/OpenAPI及其他配置所属模块内适配，所属package-info依赖、追加Common迁移、专项测试与运行文档。既有安全格式、权限、租户隔离、受保护账本和P11归属不变。

## 当前白名单清单（M3b2b）

必需集合为4个密钥域加8个配置域：common.host-policy（schema模式、浏览器来源/JSON预算、请求账本预算、可信代理）、common.cache-policy（provider/namespace/区域声明及有效策略、能力开关、Redis拓扑/逻辑DB/TLS与故障预算）、auth.session-policy、message.socket-policy、identity.session-policy、file.storage-policy、mail.work-policy、tenant.platform-policy。Tenant域覆盖平台部署操作者、入口验证和逐字段品牌默认值，不能只比较可复用的品牌revision名称。

集合按语义规范排序，数值/时间采用确定编码；品牌缺省null与空字符串保留区分。缓存每区域先摘要再合并，SMTP按路由逐项摘要。硬上限为64个来源、每域512个字段/64KiB编码、单值8192字符、集合256项；超限不可用，不截断。实际宿主完整集合验证按专项进度记录。

白名单不序列化整个Environment，也不证明代码制品兼容或所有历史密文可解密。后台worker启停角色、节点ID/端口、本地根目录路径及每节点Redis ACL凭据可以不同；存储共享和连接可用性分别由真实见证及连接工厂验证。新增影响共享状态/授权的部署配置必须由所属模块同步补入白名单和差异测试。

## M3b2c持久协议细化

复用既有common_cache_node_group/lease追加技术字段，不新增全局表例外。每清单一个32字节随机挑战，只有expected规范排序后的首节点能首次确立完整证据基线，防止错误peer抢先覆盖；这是部署指定引导节点，不是多数投票。引导节点必须由运维核对配置，初始化前其他节点只等待。基线建立后同代次不可覆盖，节点离线不会清除；配置/密钥变更必须推进既有nodes.version并按旧机制等待全部旧租约退出。

所有读写先锁group再锁自身lease并核对manifest/version/node/process/epoch/数据库租约时间；收集在事务外。每个节点报告绑定挑战、进程和epoch，成功资格最多15秒且不超过当前租约；续心跳不自动延长证据资格。旧进程、旧挑战、过期lease不能写入；不可用/不匹配报告撤销自身证据，不影响健康peer及基线。对同进程的重复完整报告可重入；未知提交只通过同绑定重新读取/报告，不建立新基线或重做业务。

按依赖先c1存储/追加迁移和真实MySQL竞争及升级，再c2独立有界宿主worker/状态与就绪联接、c3实际双JVM一致/错误钥/缺钥/配置差异/重启和peer隔离。c1不意味着服务已拒绝接流，完整b2c须后两项通过；multi始终由M3d最终门禁控制。
